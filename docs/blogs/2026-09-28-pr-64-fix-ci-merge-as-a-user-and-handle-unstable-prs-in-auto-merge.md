## fix(ci): Merge as a user and handle UNSTABLE PRs in auto-merge

- **Release tag:** `v0.0.33`
- **Source PR:** [#64](https://github.com/mpaulosky/TicketManager/pull/64)

### PR description

Ports mpaulosky/Articles#249 (a follow-up to Articles#248 and to this repo's previous auto-merge PR), which fixed two gaps.

## 1. Merges by `github-actions` skip every downstream workflow

The workflow armed auto-merge with `GITHUB_TOKEN`, so GitHub attributed the merge to `app/github-actions`. GitHub starts no workflows from events caused by `GITHUB_TOKEN`, so the merge silently skipped:

- the release workflow (no tag, no release, no release-blog PR);
- automatic issue-closing (`Closes #239` didn't close #239).

Affected so far: #248, mpaulosky/TicketManager#63 and mpaulosky/IssueManager#204. Every PR merged by `mpaulosky` today got its release and blog as normal.

**Fix:** the `github-script` step uses `RELEASE_PR_PAT` (falling back to `GITHUB_TOKEN`), the same pattern `squad-release.yml` already uses, so merges are attributed to a user.

## 2. UNSTABLE PRs can get stranded

GitHub also refuses to arm auto-merge on an **UNSTABLE** PR ("unstable status"), where the required checks have passed and only optional ones are pending or failing. mpaulosky/Blazor-Server-Template#16 went UNSTABLE, was refused, then turned CLEAN with no later event, and was never merged.

**Fix:** `decideAutoMerge` returns `merge` for UNSTABLE as well as CLEAN, and an "unstable status" refusal now falls through to a direct merge, pinned to the checked head SHA. That's what an armed auto-merge would do at that point anyway, since it only waits for required checks.

## Tests

The UNSTABLE case in `automerge-decision.test.mjs` now expects `merge` (red before, green after): **11/11**. `actionlint` and `yamllint` are clean.
